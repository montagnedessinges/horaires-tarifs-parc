# Audit de reprise — Horaires & Tarifs Parc 1.13.1

**Date :** 6 septembre 2026  
**Base auditée :** `main` — commit `d01e7e24a44f89b34ee1683709893db6f3e2ba5b`  
**Version du plugin :** `1.13.1`  
**Dépôt canonique :** `montagnedessinges/horaires-tarifs-parc`

## 1. Objet de l’audit

Cet audit prépare la prochaine évolution fonctionnelle de l’extension. Il vise à figer l’état réel de la base actuelle avant toute modification et à éviter de repartir d’une ancienne version ou de réintroduire des régressions déjà corrigées.

Il s’agit d’un **audit statique du code, de l’architecture, des tests et du processus de release GitHub**. Il ne remplace pas un test de performance chronométré sur les sites de production ni une recette visuelle complète sur les deux installations WordPress.

## 2. Référence actuelle

La version de travail n’est plus la 1.7.5. La base canonique actuelle est la **1.13.1**.

La release GitHub `v1.13.1` a été publiée automatiquement le 6 septembre 2026. Elle contient :

- `horaires-tarifs-parc.zip` ;
- le fichier `horaires-tarifs-parc.zip.sha256` ;
- un ZIP d’environ 232 Ko ;
- une empreinte SHA-256 du ZIP : `8e35eff950957786f5cb9f7c0ed81eb767129eac9fac2e67b67119b76eedf1a7`.

Le workflow de publication du commit 1.13.1 s’est terminé avec succès sur PHP 7.4, 8.1, 8.2 et 8.3. Les étapes PHP, JavaScript, tests métier/régression, nettoyage de la source de production, compatibilité/sécurité WordPress, Plugin Check officiel et publication de la release sont toutes passées.

La configuration principale reste stockée dans `parcs_ht_settings`. Le schéma actuel est `SCHEMA_VERSION = 26`.

Des options séparées existent pour les fonctions spécialisées : tarifs groupes, devis, langues de devis, accès au devis, identifiants permanents des tarifs, guides pédagogiques, apparence des guides, statistiques, sauvegardes et updater.

## 4. Moteur horaire — règles à préserver

Le moteur `Parcs_HT_Schedule` reste la source canonique de résolution d’une journée.

Ordre métier actuel :

1. vérifier que la date appartient à la saison ;
2. appliquer l’exception prioritaire ;
3. à priorité égale, une fermeture exceptionnelle prévaut sur un horaire exceptionnel ;
4. sinon appliquer l’horaire habituel correspondant au jour de la semaine ;
5. en l’absence de règle valide, considérer la journée comme fermée.

Les horaires normaux et exceptionnels acceptent un second créneau facultatif.

Les règles d’accès temporairement limité sont distinctes des horaires d’ouverture et prennent en compte les exclusions configurées : week-ends, vacances scolaires, jours fériés, périodes spécifiques et exceptions.

L’audit annuel parcourt toute la saison et détecte notamment les chevauchements d’horaires habituels et les exceptions de même priorité.

## 5. Tarifs groupes et devis — architecture 1.13

La 1.13 a introduit des identifiants permanents pour les lignes et colonnes de tarifs :

- `tariff_row_XXXXXX` ;
- `tariff_col_XXXXXX`.

Ces identifiants constituent désormais l’identité métier des tarifs et doivent survivre aux changements de libellés, traductions, prix, ordre d’affichage et duplication de saisons. Ils ne doivent pas être recyclés.

Le devis groupe ne calcule plus ses prix à partir de positions de lignes historiques. Il utilise les identifiants permanents configurés pour l’année concernée.

Le tarif utilisé dépend de l’année de la date de visite. Il n’existe pas de secours vers une ancienne année lorsqu’une grille n’est pas publiée.

Avant envoi par Contact Form 7, les prix, gratuités et totaux sont recalculés côté serveur depuis les données canoniques de l’extension. Les valeurs manipulables dans le navigateur ne sont donc pas considérées comme fiables.

La gratuité scolaire est centralisée dans `complimentary_adults()`. Avec la règle actuelle ratio 10 / seuil 5, 26 enfants donnent 3 gratuités, dans la limite du nombre d’adultes présents.

## 6. Hotfix 1.13.1

La 1.13.1 corrige la régression de l’onglet Groupes introduite en 1.13.0.

Le correctif :

- évite que le `MutationObserver` réagisse à ses propres badges et identifiants ;
- rend la décoration des lignes/colonnes idempotente ;
- groupe les rafraîchissements via `requestAnimationFrame` avec secours `setTimeout` ;
- hydrate les identifiants existants uniquement lors du passage initial ;
- évite qu’une nouvelle ligne récupère par simple position l’identifiant permanent d’une ligne existante ;
- ajoute des tests de régression associés.

Cette logique doit être conservée lors des prochaines modifications de l’administration Groupes.

## 7. Sauvegarde et intégrité

`Parcs_HT_Save_Integrity` protège les sauvegardes sensibles :

- sanitization champ par champ ;
- relecture après `update_option()` avant confirmation ;
- sauvegardes complètes quotidiennes, limitées à dix jours distincts ;
- restauration protégée par capacité et nonce ;
- sauvegarde préalable avant restauration ;
- le registre des identifiants permanents n’est volontairement jamais restauré afin que les compteurs restent monotones.

Les anciennes valeurs sont conservées lorsqu’un formulaire administratif semble tronqué ou que WordPress ne confirme pas l’écriture attendue.

## 8. Guides pédagogiques et statistiques

Les guides pédagogiques sont stockés par saison et disposent eux aussi d’identifiants permanents `guide_XXXXXX`.

Les statistiques de clics utilisent une table dédiée `{$wpdb->prefix}parcs_ht_guide_clicks` et agrègent uniquement :

- identifiant du guide ;
- année ;
- date ;
- type d’action `view` / `download` ;
- langue ;
- nombre de clics.

Le code audité ne stocke ni adresse IP, ni user-agent, ni identité du visiteur pour ces statistiques. Les événements publics sont signés par un HMAC dérivé du sel WordPress.

## 9. Updater GitHub

L’updater privé est chargé uniquement en administration ou pendant le cron.

Points positifs à préserver :

- aucun token GitHub codé dans l’extension ;
- priorité possible à une constante ou variable d’environnement serveur ;
- token WordPress chiffré en AES-256-GCM lorsqu’OpenSSL et `AUTH_KEY` sont disponibles ;
- token envoyé uniquement à `api.github.com` ;
- il n’est pas retransmis au domaine signé de téléchargement après redirection ;
- cache d’une release réussie 15 minutes ;
- cache d’erreur 5 minutes ;
- timeout de contrôle GitHub 6 secondes ;
- contrôle de l’empreinte SHA-256 avant installation du ZIP.

# 11. Anomalies et dettes identifiées

## P1 — Chargement public global du moteur devis

### Constat

Le fichier principal appelle :

```php
add_action('wp_enqueue_scripts', array('Parcs_HT_Group_Quotes', 'assets'), 30);
```

Or `Parcs_HT_Group_Quotes::assets()` charge `assets/group-quotes.js`, relit les réglages et construit le payload des saisons/tarifs publiés sans vérifier la présence d’un formulaire devis sur la page.

Par ailleurs, `Parcs_HT_Quote_Gate::init()` accroche également `assets()` à `wp_enqueue_scripts` avec la priorité 31. Tant que le module d’accès au devis est activé — valeur par défaut `1` — il charge `quote-gate.css`, `quote-gate.js` et dépend de `parcs-ht-group-quotes` sur toutes les pages publiques.

### Impact

Le moteur devis est donc actuellement préparé globalement sur le front, y compris sur des pages sans devis. Cela réintroduit un chargement contraire à l’objectif documenté en 1.9.19 : charger le moteur de devis uniquement lorsqu’un devis ou un formulaire CF7 compatible est réellement rendu.

### Recommandation

Corriger en priorité lors de la prochaine version :

- supprimer l’enqueue global de `Parcs_HT_Group_Quotes::assets()` ;
- détecter réellement la présence du shortcode devis ou d’un CF7 compatible ;
- conditionner de la même manière les assets du `Quote_Gate` ;
- conserver un fallback pour les shortcodes injectés tardivement par un constructeur de pages ;
- ajouter un test de non-régression confirmant qu’une page sans devis ne reçoit ni `group-quotes.js`, ni `quote-gate.js`, ni `quote-gate.css`.

## P2 — Budget PHP public à mesurer après l’extension fonctionnelle

Le bootstrap des shortcodes principaux reste léger et charge `class-parcs-ht-shortcodes.php` à la demande, ce qui préserve l’architecture performance introduite historiquement.

En revanche, la 1.13.1 `require_once` désormais un nombre important de classes spécialisées avant `plugins_loaded`, et initialise plusieurs modules sur toutes les requêtes publiques : tarifs groupes, statistiques/guides, devis, langues, accès au devis et dernières entrées.

Ce n’est pas en soi une preuve de ralentissement mesuré, mais le périmètre PHP public a nettement grandi. Une mesure réelle après correction P1 est recommandée avant toute nouvelle fonction importante.

Points à mesurer :

- temps PHP d’une page sans shortcode ;
- mémoire PHP ;
- nombre et poids des assets ;
- options WordPress lues ;
- page avec shortcode horaire ;
- page avec calendrier ;
- page devis ;
- page guides pédagogiques.

## P2 — Documentation de version désynchronisée

Le code et la release sont en 1.13.1, mais :

- `CHANGELOG.md` ne comporte pas de section 1.13.0 / 1.13.1 dans son état actuel et commence par 1.9.22 ;
- `readme.txt` annonce encore `Stable tag: 1.9.19` ;
- la release GitHub 1.13.1 a un `body` vide ;
- le workflow de release construit normalement le corps de la release à partir de la section correspondant à la version dans `CHANGELOG.md`.

Cela n’empêche pas le ZIP actuel de fonctionner, mais affaiblit la traçabilité et l’information affichée par l’updater.

### Recommandation

Avant ou avec la prochaine release fonctionnelle :

- reconstituer le changelog 1.10 → 1.13.1 à partir des commits/releases ;
- mettre à jour `readme.txt` ;
- ajouter un test de release qui échoue si `CHANGELOG.md` ne contient pas une section correspondant exactement à `PARCS_HT_VERSION`.

## P2 — Roadmap partiellement obsolète

`ROADMAP.md` contient encore comme évolutions prévues plusieurs fonctions déjà livrées, notamment des éléments liés aux tarifs par année, à la publication indépendante, aux identifiants permanents et au devis piloté par la date.

### Recommandation

Séparer clairement :

- livré ;
- à confirmer ;
- à faire ;
- abandonné/remplacé.

Cela évitera qu’une future reprise réimplémente une architecture déjà présente.

## P3 — Libellé interne potentiellement exposé au public

Dans `Parcs_HT_Schedule::calendar_items()`, le titre d’une période utilise le `internal_label` comme fallback lorsqu’aucun titre public traduit n’est disponible.

La documentation fonctionnelle distingue pourtant le nom/repère interne du contenu public facultatif.

### Statut

À confirmer fonctionnellement avant correction : il faut décider si l’absence de titre public doit :

1. afficher volontairement le nom interne ;
2. afficher seulement le marqueur sans texte ;
3. masquer l’élément public ;
4. utiliser une autre formulation publique générique.

Ne pas modifier ce comportement sans validation métier.

## P3 — Cron de pré-génération à documenter

Une modification de `parcs_ht_settings` incrémente `parcs_ht_export_revision` et programme un événement unique `parcs_ht_pregenerate_exports` dix secondes plus tard.

Il ne s’agit pas de l’ancien cron quotidien : celui-ci est explicitement supprimé par `Parcs_HT_Health`.

Le fonctionnement est cohérent avec une pré-génération différée des exports, mais doit rester documenté car les anciens audits 1.7.x indiquaient qu’aucun cron propre à l’extension n’existait alors.

# 12. Protections à ne pas casser dans la prochaine mise à jour

1. GitHub reste la source canonique du code.
2. Une évolution fonctionnelle = nouvelle version.
3. Ne jamais repartir d’une ancienne base 1.5.x / 1.7.x.
4. Ne jamais écraser `parcs_ht_settings` ni les options métier existantes lors d’une mise à jour de code.
5. Conserver la séparation des données MDS / FDS : même code, réglages indépendants.
6. Conserver les saisons brouillon/publiées.
7. Conserver les deux créneaux et dernières entrées indépendantes.
8. Conserver la priorité des exceptions.
9. Conserver le moteur partagé entre les shortcodes.
10. Conserver les identifiants permanents de tarifs.
11. Conserver le recalcul serveur des devis.
12. Conserver les sauvegardes restaurables et la vérification post-enregistrement.
13. Conserver le chargement conditionnel des gros modules et assets ; corriger la régression devis identifiée dans cet audit.
14. Conserver l’updater sécurisé et la vérification SHA-256.
15. Conserver la matrice CI PHP 7.4 / 8.1 / 8.2 / 8.3 et les tests métier.
16. Ajouter un test de régression pour chaque anomalie corrigée.

## Conclusion

La 1.13.1 est une base nettement plus mature que la 1.7.5 : architecture multi-saisons, tarifs et devis sécurisés par identifiants permanents, sauvegardes, guides, statistiques anonymes, updater privé avec SHA-256 et CI forte.

La principale anomalie technique à traiter avant d’ajouter de nouvelles fonctions est le **chargement public global du moteur devis et du Quote Gate**. La seconde priorité est de remettre la documentation de version en cohérence avec le code réel afin que GitHub reste une mémoire fiable du projet.
