# Audit ciblé — 27 août 2026

## Objet

Audit demandé après plusieurs correctifs 1.8.2 à 1.8.7 concernant les créneaux, dernières entrées et statuts dynamiques.

But : comprendre pourquoi La Forêt des Singes peut encore afficher un statut incohérent et éviter de multiplier les correctifs sans identifier la vraie source de l’affichage.

Aucune modification fonctionnelle n’est effectuée dans cet audit.

## Sources vérifiées

- dépôt canonique `montagnedessinges/horaires-tarifs-parc`, branche `main` ;
- page d’accueil publique La Forêt des Singes : `https://www.la-foret-des-singes.com/` ;
- page publique Horaires et tarifs La Forêt des Singes : `https://www.la-foret-des-singes.com/infos-pratiques/horaires-et-tarifs-2/` ;
- page d’accueil publique La Montagne des Singes : `https://www.montagnedessinges.com/` ;
- page publique Horaires et tarifs La Montagne des Singes : `https://www.montagnedessinges.com/infos-pratiques/horaires-et-tarifs-2-2-2/` ;
- code des moteurs JavaScript et updater GitHub ;
- workflow `.github/workflows/release.yml`.

## Constats confirmés

### 1. Les deux sites n’utilisent pas actuellement la même intégration publique

La page Horaires et tarifs de La Montagne des Singes affiche le bloc complet de l’extension : bloc Aujourd’hui, calendrier 2026, détail d’une date, résumé « Horaires du mois », tarifs.

La page Horaires et tarifs de La Forêt des Singes observée le 27/08/2026 n’affiche pas ce bloc complet. Elle affiche principalement un contenu « Horaires exceptionnels » lié aux fortes chaleurs avec l’horaire 9h–17h30, puis les tarifs et informations pratiques.

Conséquence : une correction dans l’extension ne peut pas garantir à elle seule la cohérence de tous les textes visibles sur la Forêt si une partie de l’affichage est toujours produite par le thème, Elementor, une personnalisation PHP ou un contenu de page statique.

### 2. La page d’accueil de La Forêt contient bien un libellé « Ouvert » distinct de la plage horaire

L’observation publique de la page d’accueil montre deux informations successives : « Ouvert » puis « 9h -17h30 ».

Cela est compatible avec l’hypothèse d’un ancien montage de page où le mot « Ouvert » et le shortcode horaire ne proviennent pas nécessairement de la même source.

Cette hypothèse est forte mais pas totalement confirmée tant que le thème/Elementor ou le fichier PHP correspondant n’est pas inspecté directement.

### 3. Le code possède désormais plusieurs couches qui recalculent la même information horaire

Les fichiers suivants participent au rendu dynamique :

- `assets/frontend.js` ;
- `assets/slot-last-entry-frontend.js` ;
- `assets/status-sync.js`.

`frontend.js` contient déjà des fonctions pour le statut, l’horaire d’en-tête et l’accueil.

`slot-last-entry-frontend.js` recalcule également les phases de journée (`before`, `open`, `gap`, `after`) et réécrit plusieurs composants.

`status-sync.js` ajoute une troisième synchronisation et cherche même un texte statique « Ouvert / Open / Geöffnet » dans les ancêtres du bloc horaire afin de le remplacer.

Cette duplication est fragile : ordre de chargement, cache/minification, structure Elementor ou modification du DOM peuvent faire que deux couches écrivent des valeurs différentes.

### 4. La charge JavaScript est devenue plus complexe que nécessaire

`slot-last-entry-frontend.js` lance une actualisation périodique et utilise un `MutationObserver` sur les calendriers.

`status-sync.js` lance en plus une actualisation toutes les 30 secondes et peut parcourir plusieurs niveaux d’ancêtres et interroger plusieurs sélecteurs DOM pour retrouver un libellé statique.

Ce n’est pas une charge serveur importante, mais c’est une complexité navigateur inutile si une seule source de vérité peut produire directement le bon rendu.

Recommandation : à terme consolider le statut dynamique dans un seul moteur et supprimer les couches de rattrapage devenues inutiles.

### 5. Les mises à jour automatiques peuvent réellement s’installer seules

`Parcs_HT_Updater::filter_auto_update()` renvoie `true` lorsque l’option de mise à jour automatique de l’extension est activée et qu’une clé GitHub est disponible.

Donc il est plausible qu’un site soit passé automatiquement à une nouvelle release si ce réglage est actif.

### 6. Le mécanisme de téléchargement GitHub est globalement prudent côté sécurité

Le token n’est envoyé qu’à l’API GitHub et n’est pas transmis au serveur de redirection final.

Le ZIP est vérifié avec son SHA-256 avant installation.

La vérification SSL reste active.

### 7. La compatibilité PHP est testée, mais la validation WordPress pourrait être plus stricte

Le workflow teste la syntaxe et les tests métier sous PHP 7.4, 8.1, 8.2 et 8.3.

Le plugin déclare WordPress >= 6.0 et PHP >= 7.4.

Le workflow lance également WordPress Plugin Check pour sécurité, performance et accessibilité.

Cependant :

- il n’y a pas de matrice de tests sur plusieurs versions de WordPress ;
- Plugin Check est en `continue-on-error: true`, donc une alerte ne bloque pas nécessairement la release.

### 8. Les nouveaux scripts ne sont pas tous contrôlés par le workflow

Le workflow vérifie actuellement la syntaxe de :

- `assets/admin.js` ;
- `assets/frontend.js` ;
- `assets/slot-last-entry-admin.js` ;
- `assets/slot-last-entry-frontend.js`.

`assets/status-sync.js`, ajouté ensuite, n’est pas présent dans ces contrôles.

Il faut l’ajouter si ce fichier est conservé, ou idéalement supprimer ce moteur de rattrapage après consolidation.

### 9. Le workflow peut encore écraser les assets d’une release existante

Le workflow contient une branche « Refresh existing release assets » avec `gh release upload --clobber`.

Cela est contraire à la nouvelle règle de conservation immuable des versions : un numéro déjà publié ne devrait pas recevoir un ZIP différent.

À corriger dans une future évolution du workflow : si le tag/release existe déjà, arrêter la publication au lieu d’écraser les assets.

## Cause la plus probable du problème Forêt

La cause la plus probable n’est pas seulement le calcul matin/soir.

Il existe vraisemblablement deux niveaux :

1. l’extension calcule une plage horaire ou une prochaine ouverture ;
2. un ancien élément de thème/Elementor/personnalisation PHP affiche séparément le libellé « Ouvert ».

Les versions 1.8.6 et 1.8.7 ont essayé de corriger ce deuxième niveau depuis le JavaScript de l’extension. C’est une rustine fragile car l’extension ne devrait pas avoir à rechercher et modifier arbitrairement un texte du thème.

## Ce qui ne peut pas être confirmé avec les accès actuels

Je ne peux pas confirmer quel fichier exact du thème ou quel widget Elementor contient le libellé « Ouvert » sur La Forêt des Singes, car le dépôt GitHub audité contient l’extension et pas le thème/site complet.

Je ne peux pas confirmer non plus si une ancienne modification a été faite dans `header.php`, un template Elementor, `functions.php` ou un shortcode personnalisé sans accès au code de ce thème ou à l’administration/serveur du site.

Ne pas affirmer qu’un fichier `header.php` est responsable avant cette vérification.

## Plan recommandé avant le prochain correctif fonctionnel

1. Sur La Forêt des Singes, identifier dans WordPress/Elementor le bloc exact qui affiche « Ouvert » sur l’accueil et noter son shortcode/contenu.
2. Vérifier si le bloc Horaires & Tarifs de la Forêt doit réellement utiliser l’extension complète comme la Montagne ou si le contenu exceptionnel actuel est volontaire.
3. Choisir une seule source de vérité pour statut + plage horaire + dernière entrée.
4. Intégrer cette logique directement à `frontend.js` / moteur canonique au lieu de conserver trois couches concurrentes.
5. Supprimer progressivement `status-sync.js` et toute duplication devenue inutile après validation.
6. Ajouter des tests automatisés pour les quatre phases : avant ouverture, pendant créneau, entre deux créneaux, après fermeture.
7. Ajouter des tests spécifiques aux journées à deux créneaux et aux journées matin-seul / après-midi-seul.
8. Ajouter les scripts publics réellement distribués au `node --check` du workflow.
9. Faire échouer le workflow si une version/tag existe déjà au lieu d’utiliser `--clobber`.
10. Tester les deux sites après installation, en vidant les caches WordPress/CDN/minification si nécessaire.

Un nouveau chat doit lire au minimum :

1. `CHATGPT-CONTEXT.md` ;
