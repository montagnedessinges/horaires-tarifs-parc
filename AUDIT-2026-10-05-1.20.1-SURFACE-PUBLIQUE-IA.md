# Audit 1.20.1 — surface publique, Google / IA et utilité réelle

Date : 05/10/2026  
Base auditée : `main` — commit `bbbb663c54218a4ef26cd8e04c0a9d459998a1d6` — version 1.20.1  
Issue de cadrage : #94  
Branche documentaire : `audit/1.20.2-public-ai-utility`

## 1. But de l’audit

Cet audit ne part **pas** du principe qu’une nouvelle couche IA est nécessaire.

Il doit déterminer :

1. si Google et les assistants IA grand public trouvent déjà suffisamment bien les informations publiques ;
2. si des données désactivées, internes ou hors fenêtre publique fuitent malgré tout dans une surface publique ;
3. si certaines couches historiques sont devenues redondantes et devraient être supprimées ou simplifiées ;
4. si une 1.20.2 est réellement justifiée.

Le verdict final doit être l’un des suivants :

- **A — aucune release nécessaire** ;
- **B — release corrective minimale** ;
- **C — release de simplification** ;
- **D — nouvelle couche machine réellement justifiée**.

## 2. Règle absolue retenue

> **Surface publique = surface IA / machine.**

Une information peut être exploitée par Google ou une IA si et seulement si elle est réellement publique selon les règles du plugin et du site.

Une donnée décochée, désactivée, en brouillon, hors fenêtre de publication ou réservée à l’administration ne doit pas être présente dans :

- le HTML public ;
- le JSON-LD ;
- les variables JavaScript publiques ;
- du JSON public ;
- les endpoints REST/AJAX accessibles sans authentification ;
- les attributs `data-*` ;
- les exports publics ;
- une éventuelle couche IA dédiée.

Cette règle s’applique aussi aux libellés internes et aux variantes de contenu non publiées.

## 4. Architecture de visibilité déjà en place

### 4.1 `Parcs_HT_Public_Visibility`

Le plugin possède déjà un moteur central de visibilité annuelle qui gère notamment :

- `calendar_visible` ;
- `retail_tariffs_visible` ;
- `group_tariffs_visible` ;
- `groups_schedule_visible` ;
- `group_quotes_enabled` ;
- fenêtre `public_display_from` / `public_display_until`.

Ce moteur doit devenir la référence de toute projection publique machine. Il ne faut pas recréer une deuxième logique IA.

### 4.2 `Parcs_HT_Display_Policy`

Cette couche conserve une partie des règles historiques de visibilité et de normalisation des tarifs. Elle reste utile actuellement, mais son chevauchement avec `Parcs_HT_Public_Visibility` doit être surveillé : une future simplification ne doit pas maintenir deux politiques divergentes.

## 5. Constats confirmés

### P0 — `window.ParcsHTPData` sérialise des lignes plus larges que leur surface publique réelle

`Parcs_HT_Schedule::public_settings()` sélectionne les saisons publiées, mais transmet ensuite les lignes **complètes** dès que `enabled=1` pour :

- horaires réguliers ;
- vacances scolaires ;
- périodes / événements ;
- jours fériés ;
- règles d’accès limité ;
- exceptions ;
- alertes.

Le filtrage fin est ensuite réalisé dans `frontend.js`.

Exemples :

- une période `show_on_calendar=0` est tout de même présente dans le payload avant d’être ignorée visuellement ;
- les jours fériés sont sérialisés même lorsque `show_public_holidays=0` ;
- une règle peut contenir `tooltip_text` même si son tooltip est désactivé ;
- une exception peut contenir des champs non utilisés dans sa représentation publique ;
- les lignes transportent des champs administratifs comme `internal_label` / `label` alors que le navigateur n’en a pas besoin comme donnée publique.

**Conclusion : correction nécessaire.**

La projection publique doit être assainie **avant** sérialisation, pas après réception dans le navigateur.

### P0 — fuite possible des libellés internes dans le rendu public

Deux chemins utilisent actuellement un nom interne comme repli public :

1. `assets/frontend.js` : événement / période → `translated(title) || internal_label ...` ;
2. `Parcs_HT_Schedule::calendar_items()` : `translation(title, language, internal_label)`.

Le second chemin alimente aussi le PDF planning.

Un champ intitulé « Nom interne » dans l’administration ne doit jamais devenir un texte public parce qu’une traduction publique manque.

**Conclusion : bug à corriger.**

Repli autorisé : libellé générique localisé (`Événement`, `Période`, etc.) ou absence de libellé selon le contexte ; jamais `internal_label`.

### P0/P1 — alertes historiques : projection trop large

`Parcs_HT_Schedule::public_settings()` expose les alertes avec un simple filtre `enabled=1`.

Or une alerte historique peut également posséder :

- `published` ;
- une date/heure de début ;
- une date/heure de fin.

Le moteur JS `activeAlert()` vérifie la fenêtre de dates, mais ne revérifie pas `published`.

Conséquences possibles :

- une ligne `enabled=1` mais `published=0` peut être présente dans la source publique ;
- une alerte programmée dans le futur est transmise avant d’être publiquement affichée ;
- si un vieux shortcode d’alerte est encore utilisé, la distinction admin/public peut diverger.

**Conclusion : filtrer côté PHP avant sortie et vérifier si cette ancienne surface est encore réellement utilisée.**

### P1 — portail groupes duplique la projection brute des horaires

`Parcs_HT_Group_Portal::schedule_payload()` reconstruit une seconde projection des saisons avec `enabled_rows()` et fusionne les lignes dans `window.ParcsHTPData`.

Cela reproduit le même problème que `Parcs_HT_Schedule::public_settings()` et crée deux endroits à maintenir.

**Conclusion : à simplifier.**

Si une correction est publiée, le portail groupes doit consommer une projection publique canonique commune, paramétrée par les années réellement autorisées pour les groupes.

### P1 — PDF planning public : vérifier la visibilité avant toute génération

L’endpoint `admin-post_nopriv_parcs_ht_schedule_pdf` est public et protégé par limitation de débit + `X-Robots-Tag: noindex, nofollow`, mais ce `noindex` n’est **pas** un contrôle d’accès.

`schedule_export_context()` charge `Parcs_HT_Defaults::all_settings()`, choisit une saison puis transmet les tableaux de saison complets au moteur PDF.

Sur `admin-post.php`, les filtres front basés sur `is_admin()` ne doivent pas être supposés actifs. Il faut donc garantir explicitement dans l’endpoint que l’année exportée est autorisée publiquement via `Parcs_HT_Public_Visibility`.

Le PDF utilise aussi `Parcs_HT_Schedule::calendar_items()`, donc le repli `internal_label` décrit plus haut peut s’y retrouver.

**Conclusion : correctif de garde publique recommandé.**

### P1/P2 — AJAX devis : ne pas révéler un statut calendrier hors périmètre du devis public

`Parcs_HT_Quote_Gate::date_status()` est accessible sans authentification avec nonce et retourne :

- année ;
- tarifs disponibles oui/non ;
- ouvert/fermé.

La disponibilité tarifaire s’appuie correctement sur `Parcs_HT_Group_Quotes::settings()` / `quote_enabled_for_year()`.

En revanche, `status_for_date()` peut calculer `closed` depuis la saison brute même lorsque les devis ne sont pas disponibles pour cette année.

**Décision à prendre :** lorsque `tariffs=false` / devis année non public, le endpoint ne devrait probablement pas révéler le statut horaire de cette année. À confirmer par test fonctionnel de la page devis.

### OK — FAQ publique : bonne source de vérité

La FAQ :

- possède un interrupteur global ;
- filtre les fiches `enabled` ;
- l’import ne rend publiable qu’une ligne validée avec visibilité FAQ publique ;
- ne rend pas une question/réponse vide dans la langue demandée.

`Parcs_HT_FAQ_Unified_1193` retire explicitement l’ancienne sortie publique `Parcs_HT_AI_Google::append_visit_rules` afin d’éviter deux sources de vérité.

**Conclusion : ne pas ajouter une nouvelle couche FAQ tant que les tests IA gratuits ne démontrent pas un manque réel.**

### À simplifier — ancienne base `Parcs_HT_AI_Google::knowledge`

L’ancienne base de réponses est conservée pour compatibilité/migration mais son rendu public est neutralisé par `Parcs_HT_FAQ_Unified_1193`.

Elle n’est donc plus une source publique active normale.

**Conclusion : candidat à suppression/migration définitive dans une release de simplification**, uniquement après vérification qu’aucune installation ne dépend encore de sa migration de compatibilité.

### OK — guides pédagogiques

Le stockage est permanent, mais la visibilité est gérée par année. Le rendu public filtre les guides `enabled=1` pour l’année courante/configurée.

Les statistiques utilisent des IDs et jetons dédiés ; aucune métadonnée d’administration n’est renvoyée au visiteur dans les cartes publiques.

**Conclusion : pas de nouvelle couche IA par défaut. Tester d’abord si les assistants trouvent déjà les guides publics.**

### OK — pop-up autonomes 1.20.0

La route REST publique `/parcs-ht/v1/popups` filtre avant réponse :

- `enabled=1` ;
- `published=1` ;
- date/heure courante dans la fenêtre ;
- média existant dans la langue demandée.

Elle ne renvoie pas `internal_name`.

**Conclusion : bonne architecture de projection publique. Peut servir de modèle.**

### À supprimer du paquet si confirmé mort — `class-parcs-ht-alerts.php`

Le fichier de l’ancien moteur d’alertes est toujours présent dans le dépôt, mais le bootstrap 1.20.1 ne le `require` ni ne l’initialise. Le moteur pop-up actif est `Parcs_HT_Popup_1200`.

**Conclusion : code mort probable.** Vérifier références de compatibilité/tests avant suppression du paquet.

### OK — Calendrier de l’Avent : verrouillage serveur

Les jours non encore ouverts ne sont pas simplement masqués en JS : `ajax_day()` recalcule la date d’ouverture côté serveur et renvoie 403 avant l’heure prévue.

Le mot mystère est validé côté serveur et n’est pas injecté dans le calendrier public.

**Conclusion : aucune fuite évidente détectée sur le scénario principal.**

### OK — tarifs publics

Les renderers publics filtrent :

- années autorisées ;
- lignes `enabled` ;
- offres spéciales hors fenêtre ;
- colonnes tarifaires masquées.

Les groupes disposent de leurs propres règles de publication.

**Conclusion : architecture globalement saine. Les tests IA doivent vérifier la découvrabilité réelle avant tout ajout.**

### OK / à surveiller — page devis et FAQ + Contact

Les blocs éditoriaux du devis filtrent les lignes `enabled`. Le formulaire FAQ+Contact n’est rendu que si :

- le module contact est activé ;
- Contact Form 7 existe ;
- un shortcode est configuré pour la langue.

Aucune donnée soumise par un visiteur ne doit jamais entrer dans une couche IA publique ; rien dans les renderers audités ne le fait actuellement.

## 6. Couche sémantique 1.20.1 (`Parcs_HT_Calendar_Semantic`)

Points positifs :

- aucun stockage propre ;
- respecte la visibilité générale de la saison ;
- exclut `show_on_calendar=0` pour événements/périodes ;
- n’utilise pas `internal_label` comme repli de titre ;
- respecte `show_public_holidays` ;
- traduction exacte pour les titres publics.

Questions ouvertes :

- apporte-t-elle une amélioration mesurable aux assistants IA gratuits ?
- duplique-t-elle trop le calendrier / JSON-LD sans bénéfice réel ?
- faut-il la conserver telle quelle, la réduire ou la supprimer ?

**Décision suspendue jusqu’aux tests externes.**

Les événements ne constituent pas une priorité de cette couche : lorsqu’un événement important possède une page/article public dédié, cette page doit rester la source privilégiée des moteurs et IA.

## 7. Données structurées IA & Google

La couche actuelle :

- ne remplace pas SEOPress ;
- produit `TouristAttraction` ;
- produit `OpeningHoursSpecification` et les horaires spéciaux depuis les saisons publiques ;
- se désactive si SEOPress PRO est détecté ;
- ne génère pas automatiquement de faux `Event` pour les périodes du calendrier.

**Conclusion : conserver pour l’instant.** Toute extension à d’autres contenus doit être motivée par un cas réel, pas par principe.

## 8. Événements

Principe retenu pour l’audit :

- ne pas chercher à recopier tous les événements dans une couche machine du calendrier ;
- tester d’abord les pages événement dédiées du site ;
- un événement masqué du calendrier mais publié comme article reste légitimement découvrable ;
- si un événement doit être réellement privé, sa page doit également être non publiée / non indexable et le plugin ne doit pas le divulguer.

- hallucination éventuelle ;
- besoin ou non de reformuler.

Le temps de réponse seul ne prouve pas qu’une recherche Web a été faite.

## 10. Décision provisoire après audit de code

L’audit de code ne justifie **pas**, à ce stade, une nouvelle grosse couche IA.

En revanche, plusieurs corrections de surface publique paraissent déjà justifiées indépendamment des résultats Gemini/ChatGPT :

1. créer une projection publique canonique minimale avant sérialisation JS ;
2. supprimer tout repli `internal_label` dans les renderers publics et PDFs ;
3. faire consommer cette projection au portail groupes au lieu de recopier les lignes brutes ;
4. filtrer correctement les anciennes alertes avant payload ;
5. verrouiller explicitement les exports publics sur les années/modules réellement publics ;
6. vérifier le statut renvoyé par l’AJAX devis lorsque l’année de devis n’est pas publique ;
7. retirer du paquet les couches mortes après preuve d’absence de dépendance.

Ces travaux relèvent davantage d’une **release corrective / simplification** que d’une nouvelle « couche IA ».

Le verdict final A/B/C/D reste suspendu jusqu’aux tests externes des IA gratuites.

## 11. Interdictions de conception pour la suite

- aucune modification visuelle imposée ;
- aucun texte créé uniquement pour un crawler ;
- aucun cloaking ;
- aucune seconde base de données IA ;
- aucune duplication des événements déjà correctement représentés par leurs pages dédiées ;
- aucune exposition d’un champ simplement parce qu’il est nécessaire en back-office ;
- aucune nouvelle API publique si le besoin n’est pas démontré ;
- aucune release 1.20.2 tant que la décision n’est pas prise à partir des tests + de cet audit.
