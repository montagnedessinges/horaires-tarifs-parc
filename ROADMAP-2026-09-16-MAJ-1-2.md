# Roadmap — mises à jour 1 et 2

Date : 16/09/2026

Dépôt : `montagnedessinges/horaires-tarifs-parc`

Base vérifiée au moment de la rédaction : version `1.15.12`.

Ce document sert de relais à un autre chat ou développeur. Les deux mises à jour ci-dessous doivent être développées **séparément**, avec une nouvelle version de l’extension pour chacune. Ne pas mélanger les deux lots dans une même release si ce n’est pas explicitement demandé.

# Mise à jour 1 — Recherche dans les listes d’administration

## Objectif

Ajouter un moteur de recherche/filtre instantané dans les grandes listes de l’administration afin de retrouver rapidement une entrée sans modifier les données.

Sections concernées :

1. **Périodes repères**
2. **Événements**
3. **Exceptions**
4. **Accès temporairement limité**

## Fonctionnement attendu

Chaque section concernée doit disposer de son propre champ de recherche.

La recherche doit filtrer instantanément les lignes déjà affichées dans l’administration.

Rechercher au minimum dans les informations disponibles suivantes :

- nom interne / libellé ;
- titres ;
- dates de début et de fin ;
- type lorsque cette information existe ;
- éventuellement contenu textuel utile déjà présent dans la ligne si cela ne complexifie pas inutilement le système.

La recherche doit être tolérante à la casse.

Ajouter un moyen simple de vider la recherche et de réafficher immédiatement toutes les lignes.

## Contraintes importantes

Le filtre est uniquement un outil d’interface dans l’administration.

Il ne doit :

- supprimer aucune donnée ;
- modifier aucune valeur enregistrée ;
- changer l’ordre réel des entrées ;
- perturber l’ajout de nouvelles lignes ;
- perturber la suppression ;
- perturber le tri/réordonnancement existant ;
- perturber les traductions FR / EN / DE ;
- perturber l’enregistrement de l’onglet actif ou l’enregistrement global.

Une ligne masquée par la recherche doit continuer à exister normalement dans le formulaire et ne doit pas être perdue à l’enregistrement.

## CSV — état actuel à préserver dans cette mise à jour

Le système CSV existant gère actuellement notamment :

- `regular`
- `exception_hours`
- `exception_closed`
- `holiday`
- `period`
- `school_holiday`
- `event`

Les périodes repères, événements et exceptions sont donc déjà couverts par l’import CSV.

Le module **Accès temporairement limité** n’est pas couvert par le CSV actuel.

### Important

**Ne pas modifier le système CSV dans la mise à jour 1.**

L’ajout éventuel de l’accès limité au CSV devra faire l’objet d’un lot séparé si cela est demandé plus tard.

## Interface proposée

Pour chaque liste :

- champ compact au-dessus de la liste ;
- placeholder du type `Rechercher…` ;
- compteur facultatif de résultats si simple à ajouter ;
- bouton ou icône permettant d’effacer le filtre ;
- message discret `Aucun résultat` si aucune ligne ne correspond.

## Critères d’acceptation

- [ ] Périodes repères : recherche instantanée fonctionnelle.
- [ ] Événements : recherche instantanée fonctionnelle.
- [ ] Exceptions : recherche instantanée fonctionnelle.
- [ ] Accès limité : recherche instantanée fonctionnelle.
- [ ] Une recherche vide affiche toutes les lignes.
- [ ] Une ligne masquée par le filtre reste enregistrable et n’est jamais supprimée par effet de bord.
- [ ] L’ajout d’une ligne fonctionne avec ou sans recherche active.
- [ ] La suppression d’une ligne fonctionne normalement.
- [ ] Le réordonnancement existant continue de fonctionner.
- [ ] Les traductions existantes ne sont pas affectées.
- [ ] Aucun changement de schéma de données n’est nécessaire.
- [ ] Ajouter des tests de régression si possible pour garantir que le filtrage reste purement visuel.

## Fichiers probables à modifier

À confirmer par audit avant développement :

- `includes/class-parcs-ht-admin.php` — ajout du champ de recherche et des attributs nécessaires sur les listes/lignes ;
- `assets/admin.js` — moteur de filtrage instantané ;
- `assets/admin.css` — présentation compacte de la recherche ;
- `tests/...` — nouveau test de contrat/régression admin si pertinent.

Ne pas modifier `includes/class-parcs-ht-schedule-csv.php` pour ce lot.

# Mise à jour 2 — Refonte compacte et mobile du tableau des tarifs

## Objectif général

Refondre l’affichage public des tarifs pour qu’il soit **beaucoup plus compact, plus lisible et réellement adapté aux petits écrans**.

L’aperçu actuel sur ordinateur donne une impression de nombreuses grosses cartes empilées. Sur téléphone, l’objectif est d’éviter une page tarifaire très longue et de montrer un maximum d’informations essentielles dans un espace réduit.

Le design final doit privilégier une logique de **tableau compact** plutôt qu’une succession de grosses cartes.

## Principe visuel principal

Pour l’onglet Individuels, viser une structure de ce type :

| Tarif | Sur place | En ligne |
|---|---:|---:|
| Adulte | 12 € | 12 € |
| Enfant · 5 à 14 ans | 8 € | 8 € |
| Enfant · moins de 5 ans | Gratuit | cellule en ligne masquée |

Le rendu réel doit être plus graphique qu’un tableau HTML brut, mais rester compact.

## 1. Onglets Individuels / Tarifs réduits / Groupes

Les trois onglets doivent rester **sur une seule ligne sur mobile** autant que possible.

Ils doivent être :

- compacts ;
- clairement cliquables ;
- visuellement lisibles ;
- beaucoup moins hauts que dans le rendu actuel.

Éviter les trois gros boutons empilés verticalement.

Sur très petit écran, préférer un comportement compact ou un défilement horizontal local des onglets plutôt que trois lignes verticales.

Aucun défilement horizontal de toute la page ne doit être introduit.

## 2. Tableau compact des prix

Éviter de répéter de grandes cartes `Sur place` / `En ligne` pour chaque tarif.

Les libellés des canaux peuvent être présentés une seule fois dans l’en-tête ou de manière très compacte dans les cellules.

Chaque ligne doit afficher :

- le nom du tarif ;
- le détail éventuel, par exemple `5 à 14 ans` ;
- le tarif sur place s’il est activé ;
- le tarif en ligne s’il est activé.

Réduire fortement :

- les marges verticales ;
- les paddings ;
- la hauteur des blocs ;
- les séparations inutiles.

L’objectif est une lecture rapide et immédiate sur mobile.

## 3. Couleurs distinctes Sur place / En ligne

Conserver une différence visuelle claire entre les deux canaux.

### Sur place

Style plus neutre :

- fond transparent ou neutre ;
- bordure légère ;
- prix très lisible.

### En ligne

Style légèrement plus mis en avant :

- couleur de fond différente ;
- cohérente avec les couleurs configurables du site ;
- possibilité d’une petite icône billet / web / flèche ;
- contraste suffisant ;
- rester compact, sans grosse carte.

Ne pas afficher automatiquement de mention `Meilleur tarif`, car le prix en ligne peut être identique au prix sur place.

## 4. Cellule / bloc En ligne entièrement cliquable

Lorsqu’un tarif en ligne est affiché, **toute la zone du prix En ligne doit être cliquable** et renvoyer vers la billetterie.

Le rendu doit utiliser un vrai lien accessible (`<a>`) et pas uniquement un `div` avec clic JavaScript.

### Priorité des liens

Prévoir deux niveaux :

1. **Lien spécifique au tarif** s’il est renseigné ;
2. sinon, **lien général de billetterie** déjà configuré dans l’extension.

Le système possède déjà une logique `purchase_url` pour certaines offres spéciales. Réutiliser ou généraliser cette logique proprement plutôt que créer un mécanisme parallèle inutile.

Le bouton général **Acheter vos billets** reste affiché sous le tableau lorsqu’il est configuré.

## 5. Affichage / masquage par canal et par tarif

Ajouter dans l’administration la possibilité de contrôler l’affichage de chaque canal de vente pour chaque ligne tarifaire.

Exemples :

### Adulte

- Sur place : affiché
- En ligne : affiché

### Enfant 5 à 14 ans

- Sur place : affiché
- En ligne : affiché

### Enfant moins de 5 ans

- Sur place : affiché
- En ligne : **masqué**

Une cellule masquée ne doit afficher :

- ni tiret `—` ;
- ni case vide bordée ;
- ni faux espace de prix en ligne.

Le layout doit se rééquilibrer proprement.

Si un seul canal est visible pour une ligne, il doit utiliser l’espace disponible de manière naturelle.

## 6. Enfant de moins de 5 ans

Il n’existe pas de billet en ligne à afficher pour ce tarif.

Le rendu attendu est simplement :

- libellé Enfant ;
- détail Moins de 5 ans ;
- Sur place : Gratuit.

Aucun bloc `En ligne`, aucun tiret, aucune case vide.

## 7. Tarifs réduits — uniquement sur place

Les tarifs réduits ne sont pas vendus en ligne.

L’onglet doit donc pouvoir afficher uniquement les tarifs sur place, sans colonne En ligne inutile.

Ajouter sous les onglets, lorsque `Tarifs réduits` est actif, un texte informatif personnalisable :

> Tarifs uniquement disponibles sur place.

### Ce texte doit être

- modifiable depuis l’administration ;
- activable/désactivable ;
- traduisible en FR / EN / DE ;
- affiché uniquement dans le contexte pertinent.

## 8. Mention de validité des billets en ligne

Ajouter une mention informative personnalisable :

> Les billets achetés en ligne sont valables 1 an à compter de la date d’achat.

### Ce texte doit être

- modifiable depuis l’administration ;
- activable/désactivable ;
- traduisible en FR / EN / DE ;
- compact visuellement ;
- affiché à proximité du tableau et avant ou près du bouton d’achat ;
- affiché uniquement si l’onglet actif contient au moins un tarif En ligne visible.

Ne pas afficher cette mention dans un onglet où aucun tarif en ligne n’est visible.

## 9. Responsive — contrainte forte

Le tableau doit être pensé d’abord pour les petits écrans.

Objectifs :

- fonctionnement correct dès environ 320 px de largeur ;
- pas de débordement horizontal de page ;
- onglets compacts ;
- prix lisibles sans zoom ;
- très faible hauteur par ligne ;
- pas de grosses cartes verticales ;
- conserver les informations essentielles visibles avec un minimum de défilement.

Attention : le nombre de lignes peut varier selon l’onglet et les données du parc. Ne pas promettre qu’un nombre arbitraire de lignes tiendra physiquement sur un seul écran ; l’objectif est de **minimiser fortement la hauteur** et de faire tenir les cas standards dans l’espace le plus court possible.

## 10. Administration — réglages à prévoir

Pour chaque ligne de tarif standard, prévoir au minimum :

- afficher/masquer Sur place ;
- afficher/masquer En ligne ;
- prix Sur place ;
- prix En ligne ;
- lien d’achat spécifique En ligne facultatif ;
- si lien spécifique vide : utiliser automatiquement le lien général de billetterie.

Prévoir également des réglages de texte :

### Message Tarifs réduits

- activation ;
- FR ;
- EN ;
- DE.

### Message validité En ligne

- activation ;
- FR ;
- EN ;
- DE.

Éviter d’alourdir inutilement l’administration. Les options doivent rester simples et compréhensibles.

## 11. Compatibilité avec les données existantes

La mise à jour doit conserver les tarifs déjà enregistrés.

Lors de la migration / normalisation :

- les anciennes colonnes existantes doivent rester compatibles ;
- les valeurs actuelles `Sur place` / `En ligne` ne doivent pas disparaître ;
- prévoir des valeurs par défaut qui reproduisent au maximum le comportement actuel tant que l’utilisateur n’a pas changé les nouvelles cases de visibilité ;
- ne pas casser les offres spéciales ni leur `purchase_url` actuel ;
- ne pas casser les tarifs groupes ;
- ne pas casser les exports PDF / impression existants sans avoir vérifié leur dépendance à la structure des colonnes.

## 12. Accessibilité

- Utiliser de vrais liens pour les cellules En ligne cliquables.
- Zone tactile suffisamment grande sur mobile.
- Focus clavier visible.
- Contraste suffisant entre les couleurs Sur place / En ligne.
- Les informations ne doivent pas reposer uniquement sur la couleur.
- Les onglets doivent conserver leurs attributs ARIA existants ou équivalents.

## Critères d’acceptation

- [ ] Les onglets Individuels / Tarifs réduits / Groupes sont compacts et restent sur une ligne autant que possible sur mobile.
- [ ] Le tableau est nettement plus court que l’affichage actuel.
- [ ] Les prix Sur place et En ligne ont des styles visuels distincts.
- [ ] La cellule En ligne entière est cliquable.
- [ ] Le lien spécifique par tarif est utilisé s’il existe.
- [ ] Sinon le lien général de billetterie est utilisé.
- [ ] Le bouton général Acheter vos billets reste disponible.
- [ ] Sur place peut être masqué par tarif.
- [ ] En ligne peut être masqué par tarif.
- [ ] Une cellule masquée ne laisse ni tiret, ni case vide, ni faux espace.
- [ ] Enfant moins de 5 ans peut afficher uniquement Gratuit sur place.
- [ ] Tarifs réduits peut fonctionner sans aucun tarif En ligne.
- [ ] Le texte `Tarifs uniquement disponibles sur place.` est modifiable, traduisible et activable/désactivable.
- [ ] Le texte de validité 1 an est modifiable, traduisible et activable/désactivable.
- [ ] La mention 1 an ne s’affiche que s’il existe au moins un tarif En ligne visible dans l’onglet actif.
- [ ] Affichage correct à 320 px de large.
- [ ] Aucun scroll horizontal de toute la page.
- [ ] Les tarifs existants sont conservés après mise à jour.
- [ ] Les tarifs spéciaux existants continuent de fonctionner.
- [ ] Vérifier les PDF / impressions après modification de la structure des tarifs.

## Fichiers probables à modifier

À confirmer par audit avant développement :

- `includes/class-parcs-ht-admin.php` — nouveaux réglages par ligne + messages configurables ;
- `includes/class-parcs-ht-defaults.php` — nouvelles valeurs par défaut / normalisation si nécessaire ;
- `includes/class-parcs-ht-shortcodes.php` — nouveau rendu compact du tableau et liens En ligne ;
- `includes/class-parcs-ht-display-policy.php` — si les nouvelles propriétés doivent être normalisées dans les saisons publiques ;
- `assets/frontend.css` — refonte responsive du tableau ;
- `assets/frontend.js` — uniquement si nécessaire pour interaction/onglets, éviter de déplacer inutilement le rendu en JavaScript ;
- `assets/admin.js` — uniquement si nécessaire pour les nouveaux contrôles de visibilité ;
- tests existants autour des tarifs + nouveaux tests de régression.

## Tests à examiner en priorité

Le dépôt contient déjà des tests autour de l’affichage et des tarifs. Vérifier notamment les contrats et tests runtime liés à :

- publication des tarifs ;
- affichage des tarifs ;
- shortcodes tarifs ;
- données publiques ;
- UI publique ;
- politique d’affichage ;
- offres spéciales.

Adapter les tests existants plutôt que dupliquer inutilement la couverture.

# Rappel important pour le prochain chat / développeur

Avant toute modification :

1. vérifier la version réellement présente sur `main` ;
2. repartir du code actuel et non d’une ancienne archive ;
3. auditer les fichiers concernés avant d’écrire ;
4. préserver les optimisations et mécanismes de compatibilité existants ;
5. ne pas développer les deux mises à jour simultanément si l’utilisateur souhaite continuer à les valider étape par étape.
